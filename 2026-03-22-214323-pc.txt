  可行性判断：可行，但改造量大

  唯一现实可行的框架是 Taro（京东出品），原因：

  1. Taro 支持 React 语法 — 你的项目是纯 React + Hooks，Taro 3.x 以 React
  为第一公民，JSX/Hooks/函数组件可以大量复用
  2. Taro 编译到 H5 + 微信小程序 — 一套代码同时输出 Web 和小程序
  3. 有配套 UI 库 — @taroify（类 Vant）或 taro-ui 可替代 antd-mobile
  4. 社区成熟 — 微信小程序 React 方案中 Taro 是最主流的

  为什么不选其他：
  - uni-app — 基于 Vue，你的项目是 React，迁移等于重写
  - Remax — 已停止维护
  - 直接用微信原生 — 无法复用任何现有代码

⏺ 1. 新建工程 vs 改造现有工程

  原因：

  ├──────────┼────────────────────────────────────────┼─────────────────────┤
  │ 构建系统 │ Vite 要换成 Taro CLI，现有 PC          │ 各自独立，互不干扰  │
  │          │ 端构建被破坏                           │                     │

  │ 依赖冲突 │ antd-mobile、dnd-kit、react-router     │ 各自按需安装        │

  │          │                                        │ 包复用逻辑层        │
  ├──────────┼────────────────────────────────────────┼─────────────────────┤
  │ 发布节奏 │ PC 和小程序被绑定在一起                │ 独立版本、独立发布  │

  huodongjia/

  2. 商家端是否需要上小程序

  结论：不需要，保持 PC Web。

  理由：

  - 使用场景不同 — 商家管理活动（创建/编辑活动、报名管理、数据导出、匹配配置）都
  是重操作，需要大屏、键盘、表格、批量处理，小程序的交互空间根本不够
  - 你的商家端功能复杂度高 — Dashboard 统计图表、报名列表筛选/导出 Excel、拖拽排
  序（dnd-kit）、富文本编辑，这些在小程序上要么无法实现，要么体验极差
  - 用户群体小 — 商家/主办方是少数人，让他们用 PC 管理是合理的
  - 投入产出比差 — 迁移商家端的工作量比 C
  端大（表格、导出、拖拽），但使用频次远低于 C 端

  如果商家有移动端需求，建议只做轻量通知类功能（如"有新报名"推送），通过微信服务
  号消息模板即可实现，不需要独立小程序页面。

  3. 后端是否需要修改

  大部分情况不需要，但有几个点必须处理：

  不需要改的

  - REST API 接口本身 — 小程序和 Web 调用同一套接口，请求/响应格式不变
  - 业务逻辑 — 活动、报名、匹配等核心逻辑与前端平台无关
  - 数据库 — 不受影响

  必须新增/修改的

  (1) 微信小程序登录流程（最大改动）

  这是最关键的后端改动。当前 Web
  端的登录是用户名/密码，小程序必须走微信授权登录：

  Web 端登录：
    用户名 + 密码 → POST /auth/login → 返回 JWT token

  小程序登录（微信要求的流程）：
    wx.login() → 获取 code
      ↓
    小程序将 code 发给后端 → POST /auth/wx-login
      ↓
    后端用 code 调微信服务器 → 换取 openid + session_key
      ↓
    后端根据 openid 查找/创建用户 → 返回 JWT token

  后端需要新增：
  - POST /auth/wx-login 接口 — 接收微信 code，调用微信 jscode2session API
  - 用户表新增 openid、union_id 字段（关联微信身份）
  - 首次登录时的用户自动注册/绑定逻辑
  - 微信手机号获取接口（可选，获取用户手机号需要额外解密）

  (2) 微信支付（如果有付费活动）

  - 需要接入微信支付 API（与 Web 端支付宝/网页支付不同）
  - 后端需新增微信支付下单、回调通知接口

  (3) 小程序消息订阅推送

  - 如需推送"报名成功"、"活动开始"等通知
  - 后端需对接微信订阅消息 API（subscribeMessage.send）

  你的认证方案建议

  小程序端登录设计：

  1. 打开小程序 → 静默调用 wx.login() 获取 code
  2. 发送 code 到后端 → POST /auth/wx-login
  3. 后端换取 openid → 查找已有用户
     ├── 已有用户 → 直接返回 JWT token
     └── 新用户 → 创建账户，返回 JWT token + needProfile: true
  4. 如果是新用户 → 引导填写昵称/头像（可选获取手机号）
  5. 后续所有请求携带 JWT token（与 Web 端一致）

  这样设计的好处是：JWT token 鉴权机制与 Web 
  端完全一致，除了登录入口不同，后续所有 API
  调用都走同一套认证中间件，后端改动最小。

  其他小程序特有限制

  - 包体积限制：主包 2MB，分包每个 2MB，总计 20MB — 需注意图片资源走 CDN
  - 审核要求：需要营业执照主体、类目资质（活动类可能需要特定类目）
  - 隐私协议：需在小程序内展示隐私政策（你已有 PrivacyPolicy.tsx，内容可复用）
  - 内容安全：用户生成内容需接入微信内容安全 API 做审核

❯ 如果已经要单独做小程序的功能,担仍希望最大程度的代码复用，还需要使用taro这个框 
架吗                                                                            

⏺ 这个问题问到了关键点。答案是：不一定需要 Taro，原生小程序可能更合适。

  核心逻辑

  你能复用的代码本质上是纯 TypeScript 逻辑，跟用不用 Taro 无关：

  可复用层（与框架无关）        不可复用层（必须重写）
  ─────────────────────        ─────────────────────
  types/    类型定义             UI 组件（JSX → WXML）
  store/    Zustand 状态         样式（Tailwind → WXSS）
  services/ API 接口定义         路由（React Router → 页面配置）
  utils/    纯函数工具           表单（react-hook-form → 原生）
  hooks/    纯业务逻辑部分        布局（HTML div → view）

  这些文件直接复制到原生小程序工程里一样能用。Taro 的价值在于让你用 JSX 写 
  UI，但既然 UI 层无论如何都要重写，这个价值就大打折扣了。

  Taro vs 原生小程序对比

  ┌────────────────┬──────────────────────────────┬──────────────────────────┐

  什么时候该用 Taro

  只有一个场景值得用：你确定近期还要出支付宝小程序、抖音小程序。这时 Taro
  的一码多端才有真正价值。

  如果只做微信小程序，Taro 反而是负担。

  request.ts 适配示例（唯一需要改的底层）：

  // shared/services/request.ts
  // 替代 axios，接口签名一致，上层 API 函数无需改动

  interface RequestOptions {
    url: string
    method?: 'GET' | 'POST' | 'PUT' | 'DELETE'
    data?: any
    headers?: Record<string, string>
  }

  export const request = <T>(options: RequestOptions): Promise<T> => {
    const token = wx.getStorageSync('auth-token')
    return new Promise((resolve, reject) => {
      wx.request({
        url: BASE_URL + options.url,
        method: options.method || 'GET',
        data: options.data,
        header: {
          'Content-Type': 'application/json',
          ...(token ? { Authorization: `Bearer ${token}` } : {}),
          ...options.headers,
        },
        success: (res) => resolve(res.data as T),
        fail: (err) => reject(err),
      })
    })
  }

  上层 API 函数几乎不用改：

  // shared/services/activityApi.ts
  // 只改 import 来源，函数体不变
  import { request } from './request'

  export const getActivities = (params: ActivityQuery) =>
    request<ActivityListResponse>({ url: '/activities', method: 'GET', data:
  params })

  export const getActivityDetail = (id: string) =>
    request<Activity>({ url: `/activities/${id}` })

  结论

  ┌──────────────────────────┬──────────────────────────────────────────────┐
  │           问题           │                     回答                     │
  ├──────────────────────────┼──────────────────────────────────────────────┤
  │ 只做微信小程序要不要     │ 不需要，原生更简单直接                       │
  │ Taro                     │                                              │
  ├──────────────────────────┼──────────────────────────────────────────────┤
  │ 代码复用靠什么           │ 靠共享 TypeScript 逻辑层，与框架无关         │
  ├──────────────────────────┼──────────────────────────────────────────────┤
  │ 复用率能到多少           │ 逻辑层 70-80%，UI 层                         │
  │                          │ 0%（无论用什么方案都要重写）                 │
  ├──────────────────────────┼──────────────────────────────────────────────┤
  │ 什么时候该用 Taro        │ 确定要同时出 2 个以上平台的小程序时          │
  └──────────────────────────┴──────────────────────────────────────────────┘

  简单说：Taro 解决的是"多端小程序"的问题，不是"Web 
  和小程序共享代码"的问题。你要的共享代码，直接复制 TS 文件就能实现。
